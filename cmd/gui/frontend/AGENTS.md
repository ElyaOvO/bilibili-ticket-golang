# 前端 UI 设计准则

本文件适用于 `cmd/gui/frontend/`。同时继承仓库根目录 `AGENTS.md`；发生冲突时，以本文件对前端 UI 的更具体要求为准。

## 设计目标

本应用是桌面端集群与任务管理工具，不是营销网站。界面应优先保证：

1. 状态一眼可辨：账号、Worker、任务、订单和错误状态必须清楚。
2. 高频操作高效：减少不必要的跳转、弹窗和视觉装饰。
3. 危险操作可控：停止、删除、强制连接等操作必须明确后果并防止误触。
4. 长时间使用舒适：支持系统明暗主题，保持稳定的信息密度和视觉层级。
5. 中英文均可用：布局必须容纳英文文案变长，不能只针对中文宽度设计。

## 视觉语言

- 延续 Vuetify 4、Roboto、Material Design Icons 和当前 `system` 主题，不另建一套组件或主题系统。
- 界面应克制、清晰、偏工具型。避免大面积渐变、玻璃拟态、霓虹发光、过重阴影、纯装饰插画和无意义动画。
- 优先使用 Vuetify 的语义色 `primary`、`success`、`warning`、`error`、`info` 及 `surface` 系列；不要为普通状态硬编码十六进制颜色。
- 颜色必须表达稳定语义：
  - `success`：在线、健康、完成、可用。
  - `warning`：降级、临近截止、需要关注、风险提示。
  - `error`：失败、离线、阻断、不可逆危险操作。
  - `info`：中性说明、进行中、辅助信息。
- 不只用颜色区分状态；同时使用文本、图标、chip 标签或形状。
- 卡片默认使用 `outlined` 或低强调的 `tonal` 表现层级，圆角以 `rounded="lg"` 或项目已有样式为主。仅浮层、菜单、关键对话框使用明显 elevation。
- 图标优先使用 `mdi-*`。Emoji 只用于已有内容语义或刻意的轻量提示，不作为主要导航和操作图标。

## 页面结构

- 保持 `App.vue` 中现有导航抽屉和全局内容容器模型；没有明确需求时不要重构全局导航。
- 标准页面使用以下层级：页面标题栏 → 页面级提示/摘要 → 筛选与主操作 → 主内容 → 空状态或辅助说明。
- 页面标题沿用 `.page-title-bar` 与 `.page-title`。标题栏右侧只放页面级主操作、刷新或紧密相关的筛选器。
- 使用 `v-container`、`v-row`、`v-col` 和 Vuetify 间距工具组织布局。间距优先采用 4px 倍数，常用为 8、12、16、24、32px。
- 遵循全局约 1185px 的最大内容宽度。表单和确认对话框不要无理由拉满整个页面。
- 相关内容成组，不相关内容不要塞入同一张卡。一个区域只保留一个清晰的视觉重点。
- 页面不应产生无意义的水平滚动。数据确实很宽时，可让表格区域独立横向滚动，并固定或保留关键操作列的可见性。

## 信息层级与排版

- 每页只使用一个主标题。卡片标题、分区标题和正文应有明显但不过度的字号/字重差异。
- 正文优先使用 Vuetify 的 `text-body-*`、`text-medium-emphasis` 等排版类，不随意定义近似字号。
- 标签简短明确；解释性文本放在 subtitle、hint、alert 或 tooltip 中，不把一整段说明塞进按钮。
- ID、地址、版本、时间戳等机器信息可使用等宽样式，并支持选择/复制；不要让长值撑破布局。
- 时间、延迟、数量、状态等高频信息保持格式一致，单位不得缺失。

## 组件选择

- 集合数据优先使用 `v-data-table`/`v-table`；概览或少量对象可使用卡片列表。不要用大量卡片模拟本应可比较的表格。
- 状态使用紧凑 `v-chip`，沿用全局表格 chip 高度；chip 文案应短，不承载操作。
- 主操作使用有文字的按钮；仅当图标含义普遍且上下文明确时使用 icon button，并提供 `aria-label` 和必要的 tooltip。
- 同一区域最多有一个高强调主按钮。次要操作使用 `outlined` 或 `text`，危险操作使用 `error`，但不要让整页充满红色按钮。
- 高频、低风险操作可直接执行；不可逆或影响多个对象的操作必须使用确认对话框，并明确对象、数量和后果。
- 不把普通确认塞进浏览器原生 `confirm()`；使用 Vuetify dialog，保持键盘焦点和视觉一致性。
- 表单控件默认使用现有的 `outlined` 风格。紧凑工具栏可用 `density="compact"`，主要录入表单不要为了省空间牺牲可读性。
- 复用 `components/`、`composables/` 和现有 picker 组件。相同交互出现两次以上时，应优先抽取共用实现。

## 表单与操作反馈

- 表单字段必须有可见 label；placeholder 只给示例，不能代替 label。
- 必填、格式、范围和字段间约束应尽量在提交前验证，错误提示靠近对应字段。
- 数字输入必须标明单位和合理范围；毫秒、端口、并发数等不得依赖用户猜测。
- 提交期间显示 loading 并阻止重复提交；不要让用户怀疑按钮是否生效。
- 成功反馈使用现有 snackbar；局部可恢复错误优先在组件附近显示，全局/操作错误使用 `useMessagesStore()`。
- 错误文案应说明“发生了什么”和“用户可以做什么”，不要只显示 `失败` 或裸错误码。
- 保存后若仍停留在当前页面，应及时刷新相关局部状态，不要求用户手动刷新才能看到结果。

## 异步与数据状态

每个依赖异步数据的主要区域都要考虑以下状态：

- 首次加载：使用 skeleton 或明确的 loading 状态，避免空白页面。
- 后台刷新：保留已有内容，只在刷新按钮或局部区域显示进度，避免整页闪烁。
- 空状态：说明为什么为空，并在合适时提供一个明确的下一步操作。
- 错误状态：使用 alert 或局部错误面板，保留重试入口；有旧数据时不要轻易清空。
- 部分成功：批量操作逐项展示成功/失败，不能用一个总提示掩盖失败对象。
- 实时状态：轮询和事件更新不得造成布局跳动、重复 snackbar 或持续抢夺焦点。

## 响应式与窗口尺寸

- 虽然应用以桌面端为主，页面仍需在较窄窗口中可操作。优先让工具栏换行、列降级或区域滚动，而不是裁切内容。
- 不依赖固定像素定位完成主布局。必要的宽度限制应使用 `max-width`，并为长文案和长值预留伸缩空间。
- 宽表格在窄窗口可隐藏低优先级列，但账号、Worker/任务名称、主要状态和操作入口必须保留。
- 对话框在普通桌面窗口内必须完整可见；内容过长时让正文区滚动，标题和操作区保持可达。

## 明暗主题与无障碍

- 所有新增 UI 都必须同时适配浅色和深色主题。不要假设背景永远是白色，也不要用固定浅灰文本。
- 文本与背景保持足够对比度；弱化信息使用 Vuetify emphasis token，不以极低 opacity 隐藏重要内容。
- 所有交互应可通过键盘完成，并保留清晰的 focus 样式。不要用 `div` 点击事件代替按钮。
- icon button 必须有可访问名称。装饰图标不应被读屏器重复朗读。
- 常规点击目标应足够大；`x-small` 仅用于表格行等高密度次要操作，且必须有 tooltip/label。
- 动画应短且服务于状态变化，遵守已有 `prefers-reduced-motion` 处理；禁止循环装饰动画。

## 国际化与文案

- 用户可见文案必须通过 `vue-i18n`，同步更新 `src/locales/zh-CN.json` 和 `src/locales/en-US.json`。
- 禁止在模板或脚本中新增仅中文/仅英文的按钮、标题、提示和错误文案。
- 文案简洁、具体、面向动作。按钮使用动词，例如“保存设置”“重新连接”，避免含糊的“确定”“处理”。
- 插值参数使用有意义的名称，并保证两种语言的变量集合一致。
- 布局至少按英文比中文长约 30% 的情况设计；不要用截断掩盖关键操作或状态。

## 实现边界

- 优先使用 Vuetify props 和工具类；只有跨组件复用或 Vuetify 无法表达时才新增 SCSS。
- 页面私有样式放在对应 `.vue` 的 scoped style；真正全局的规则才进入 `src/styles/` 或 `App.vue` 全局样式。
- 避免大量 inline `style`。确需动态值时使用 CSS 变量，固定规则使用 class。
- 不手工修改 `bindings/` 和 `src/components.d.ts`。不要为了视觉改动改变 Wails API 数据结构，除非任务明确需要端到端调整。
- 新依赖必须有明确收益；能用 Vuetify、Vue 和现有工具实现时，不引入新的 UI/动画/图标库。

## UI 改动检查

完成 UI 任务前，至少确认：

1. 页面符合现有导航、标题栏、容器、卡片和表格语言。
2. loading、空、错误、成功及禁用状态均有合理表现。
3. 浅色、深色主题下信息可读，危险和普通操作层级正确。
4. 中文和英文文案齐全，英文长文案不会破坏布局。
5. 键盘操作、焦点、icon button 标签和 reduced-motion 没有退化。
6. 在常规桌面窗口和较窄窗口下检查溢出、换行、表格与对话框。
7. 运行：

```powershell
npm run type-check
npx eslint .
npm run build
```

`npm run lint` 会自动修改文件；仅验证时继续使用非修改式的 `npx eslint .`。
